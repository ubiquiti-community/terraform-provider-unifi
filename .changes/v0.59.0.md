## [v0.59.0] - 2026-10-03

Five fixes to one defect class, each measured against a live controller rather
than inferred from the schema: an `Optional + Computed` attribute that also
carries a static `Default` overwrites whatever the controller holds. The
framework applies defaults (`TransformDefaults`) *before* it runs plan
modifiers (`SchemaModifyPlan`), so the `Default` wins and pairing it with
`UseStateForUnknown` does **not** protect an adopted resource - a point worth
remembering beyond these attributes (#544 tracks the remaining ones).

**If you create resources without declaring these attributes, read the entries
below**: thirteen attributes on `unifi_wlan` and `unifi_network` no longer fall
back to a provider-side constant, so a new SSID or network that relied on one
must now set it explicitly. `unifi_firewall_policy.ip_version` is the exception
- the controller rejects a create without it, so it still defaults to `IPV4`,
but only when the policy is being created. Nothing changes for an existing
resource except that the provider stops proposing to overwrite it.

### 🐛 Bug Fixes

- **`unifi_network`: `setting_preference` and `ipv6_interface_type` no longer overwrite the controller's value on an adopted network.** Same defect as #543 and #546: both were `Optional + Computed` and also carried a static `Default`, and the framework applies defaults (`TransformDefaults`) *before* it runs plan modifiers (`SchemaModifyPlan`), so the `Default` wins. Measured on a live twelve-network site, 11 of 12 networks store `setting_preference = "manual"` against an `auto` default, and 6 of the 9 that report it store `ipv6_interface_type = "static"` against a `none` default - so importing a network proposed **cutting its static IPv6** (`static` -> `none`) and switching it to controller-managed (`manual` -> `auto`), which also resets DHCP guarding. Both defaults are dropped in favour of `UseStateForUnknown`; the read path already normalizes a field the controller omits to `none` / `default` (#414), so nothing else changes. A configuration relying on the old defaults for a **new** network must set them explicitly (#544)
- **`unifi_wlan`: nine more attributes no longer overwrite the controller's value on an adopted SSID, four of them security settings.** Same defect as #543, found by cross-referencing every `Optional + Computed` attribute that also carries a static `Default` against a live six-SSID site: the framework applies defaults (`TransformDefaults`) *before* it runs plan modifiers (`SchemaModifyPlan`), so a `Default` always beats the controller's value for an attribute the configuration does not set. `wpa3_support`, `wpa3_transition`, `pmf_mode`, `bss_transition`, `hide_ssid`, `no2ghz_oui`, `enhanced_iot`, `wlan_band` and `wlan_bands` each disagreed with what the controller actually stores on at least two of the six SSIDs. Measured on a real WPA3 SSID, importing it proposed **turning WPA3 off** (`wpa3_support`, `wpa3_transition` true -> false), **dropping 802.11r roaming** (`bss_transition` true -> false) and **disabling management-frame protection** (`pmf_mode` `optional` -> `disabled`) - a silent security regression, with nothing in the configuration asking for it. All nine defaults are dropped in favour of `UseStateForUnknown`, matching the neighbouring attributes, and the guard test now covers all eleven. A configuration relying on the old defaults for a **new** SSID must set them explicitly (#544)
- **`unifi_device`: a `config_network` change no longer deletes the sibling keys it leaves at their zero value.** `config_network` is a full replace on the controller - a key the PUT body leaves out is *deleted* from the stored object, not left untouched - and go-unifi marked every field `omitempty`, so the fields whose ordinary value *is* the zero value never reached the wire: `bonding_enabled = false` on any switch, and `dns2 = ""` whenever a single resolver is set. Changing `dnssuffix` therefore wrote a body without those two keys, the controller dropped them, and the provider read them back as absent, failing the apply with `Provider produced inconsistent result after apply` and aborting every later change in the same run. Measured on a UCG-Fiber running Network 10.6.106: a write omitting the two keys removed them from the stored object, and re-sending them explicitly restored it. `bonding_enabled`, `dns1`, `dns2`, `dnssuffix` and `gateway` are now always serialized (the controller accepts and stores an empty value for each); `ip`, `netmask` and `type` stay omitted when empty, since a static `config_network` is rejected without them. Verified live: changing `dnssuffix` now leaves `bonding_enabled` and `dns2` intact and the next plan is clean. The `lifecycle { ignore_changes = [config_network] }` workaround can be removed. Requires go-unifi ≥ v1.36.0 (ubiquiti-community/go-unifi#89) (#542)
- **`unifi_firewall_policy`: `ip_version` no longer narrows an adopted policy to IPv4.** The attribute was `Optional + Computed` and also carried a static `Default` of `IPV4`, and the two contracts conflict: the framework applies defaults (`TransformDefaults`) *before* it runs plan modifiers (`SchemaModifyPlan`), so the default wins over `UseStateForUnknown` and an undeclared `ip_version` is planned at `IPV4` whatever the controller holds. Measured on a 372-policy site, 301 policies store `BOTH` and 9 store `IPV6`, so importing almost any policy proposed stripping its IPv6 scope - with nothing in the configuration asking for it. The default cannot simply be dropped either: the controller requires the field on both POST and PUT (`ip_version: must not be null`), so a create with no value fails. It is now applied by a new create-only plan modifier: `IPV4` is still planned when the resource is being created, and the controller's value is held on every subsequent plan (#544)
- **`unifi_wlan`: `group_rekey` and `wpa_enc` no longer overwrite the controller's value on an adopted SSID.** Both were `Optional + Computed` and also carried a static `Default`, and the two contracts conflict: `Optional + Computed` means "take the controller's value when unset", `Default` means "plan this constant", and `Default` wins. So an undeclared attribute was planned at the constant and written on apply. Measured on a six-SSID site, five stored `group_rekey = 0` against a default of `3600` and two stored a `wpa_enc` other than `ccmp`, so a plan proposed turning group rekeying on where it was deliberately disabled and changing the encryption mode - with nothing in the configuration asking for it. Both defaults are dropped, keeping `UseStateForUnknown`, matching the neighbouring attributes. A configuration relying on the old defaults for a **new** SSID must now set them explicitly (#543)

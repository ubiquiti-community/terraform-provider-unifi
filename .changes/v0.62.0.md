## [v0.62.0] - 2026-10-31

New resources for QoS rules, content filtering, NAT rules and traffic
matching lists, a Teleport data source, and new `unifi_setting` sections for
SNMP, Multicast DNS, Channel AI and Etherlighting. `unifi_setting`,
`unifi_network` and `unifi_wan` updates now send only what the plan changes,
and an imported `unifi_setting` reads every section. go-unifi is now v1.41.0.

**Upgrade notes:**

- `unifi_device`: `port_override` booleans now send an explicit `false`. A
  configured `autoneg = false` (or any other `false` port override boolean)
  used to be dropped from the request, so the controller kept `true`; it is
  now sent with the next update of the device's port overrides. `port_override.tagged_networkconf_ids` is now sent and
  read when it is set, where it used to be silently ignored.
- `unifi_site_to_site_vpn`: IKE phase 1 settings are now sent and read as
  `ipsec_ike_encryption`, `ipsec_ike_hash` and `ipsec_ike_dh_group` instead of
  the generic `ipsec_encryption`, `ipsec_hash` and `ipsec_dh_group`.
- `unifi_qos_rule` and `unifi_content_filter`: removing every entry from a
  list attribute (or dropping one that was set) recreates the object, because
  the API cannot clear a list in place; an explicitly empty list (`[]`) is
  rejected.
- `unifi_traffic_matching_list` uses the UniFi Network Integration API, which
  only accepts API key authentication: configure the provider with `api_key`.

### ✨ Features

- **New resources `unifi_qos_rule` and `unifi_content_filter`.** `unifi_qos_rule` manages a QoS rule (Settings > Routing > QoS): `objective` (`PRIORITIZE`, `LIMIT` or `LIMIT_AND_PRIORITIZE`), download and upload limits and bursts, an optional `wan_or_vpn_network`, and nested `source` (`ANY`, `CLIENT` or `NETWORK`), `destination` (`ANY`, `APP`, `APP_CATEGORY`, `IP`, `IID`, `REGION` or `WEB`, with an optional port match) and `schedule`. `unifi_content_filter` manages a content filter (Settings > Security > Content Filtering): `network_ids` or `client_macs`, blocked `categories`, `allow_list`, `block_list`, `safe_search` (`GOOGLE`, `YOUTUBE`, `BING`) and `schedule`. Both import by `id` or `site:id`. Lists the controller returns empty read as null, and the defaults (`ANY` source and destination, no port match, `ALWAYS`) are not stored, so a configuration that leaves them out does not drift. Removing every entry from a list recreates the object, because go-unifi sends the lists with `omitempty` and an update could not clear them (#659, from #563 by @kubicgruenfeld)
- **New resource `unifi_nat`.** Manages a gateway NAT rule: `type` (`DNAT`, `SNAT` or `MASQUERADE`), `in_interface` / `out_interface`, the translated `ip_address` and `port`, `protocol`, `ip_version`, `exclude`, `logging`, `pppoe_use_base_interface`, `rule_index`, and `source_filter` / `destination_filter` matching by address and port, firewall groups or network. Ports are strings: `source_filter.port` and `destination_filter.port` accept a single port (`443`) or a range (`8080-8090`), while the translated `port` takes a single port (1-65535), because the controller rejects a translated range with `NatRuleInvalidParameters`. Rules can be imported (#667, from #578 by @denisyfrolov; #579; #670)
- **New resource and list resource `unifi_traffic_matching_list`.** Manages a reusable list of IPv4 addresses or ports (`type` `IPV4_ADDRESSES` or `PORTS`, `items`) for firewall and traffic-management rules, and lists the existing ones in a site, filtered by `name` or `type`. Both use the UniFi Network Integration API, which addresses sites by UUID: the configured `site` (name or UUID) is resolved to its UUID, while state keeps the value you set. The Integration API only accepts API key authentication, so the provider must be configured with `api_key` (#658, from #576 by @denisyfrolov; #577)
- **New data source `unifi_teleport`.** Reads a site's Teleport settings: `enabled` and `subnet_cidr` (#665, from #588 by @denisyfrolov; #589)
- **`unifi_setting`: `snmp` block.** Manages the SNMP agent (Settings > System > SNMP): a v1/v2c `community` (`enabled`) and one SNMPv3 user (`enabled_v3`, `username`, `password`). `password` is stored in state and kept on read, because controllers may omit or mask it, so a password changed outside Terraform is not detected; the write-only `password_wo` (Terraform 1.11+) with `password_wo_version` is the alternative that never stores it. Writes overlay the configured values on the controller's document, so unmanaged fields are kept. Only a configured `snmp` block is read; import does not populate it (#651, from #485 by @jaxzin)
- **`unifi_setting`: `mdns` block.** Manages Multicast DNS (Settings > Networks > Multicast DNS): `mode` (`all`, `auto` or `custom`), `enabled_for` (`all`, `some` or `none`), `predefined_services`, `custom_services`, and the read-only `enabled_for_network_ids`. With `enabled_for = "some"` the networks are chosen with `multicast_dns` on `unifi_network`: the controller derives the list from each network's flag and ignores writes to it. Options the block does not expose keep their controller values (#661, from #562 by @kubicgruenfeld)
- **`unifi_setting`: `radio_ai` block for Channel AI.** Manages the nightly channel optimization (Settings > WiFi > Channel AI): `enabled` (the `cron_expr` schedule), `auto_enabled` (the controller's separate automatic-optimization flag), `cron_expr`, `radios`, `optimize`, `channels_ng` / `channels_na` / `channels_6e`, `exclude_devices`, plus `setting_preference`, `auto_channel_presets_type`, `auto_adjust_channels_to_country`, `ht_modes_ng` / `ht_modes_na`, `high_priority_devices`, `channels_blacklist` and `radios_configuration`. The optimizer rewrites the channel of every radio in the bands listed in `radios`, overriding a channel set on the device, so leaving a band out of `radios` pins its channels. Writes are partial: only configured attributes whose value differs from the controller's document are sent, and the rest keep their controller values. An attribute left unset stays null instead of being filled from the controller after apply. The plan fails when `channels_na` lists DFS channels (52-144) while the `na` entry of `radios_configuration` has `dfs = false`, or when `ht_modes_ng` / `ht_modes_na` include a width above that band's `channel_width`, since the controller would silently drop them. `radio_ai` is not read on import (#650, from #630 by @johnmerchant; #661 and #671, from #562 by @kubicgruenfeld; #629)
- **`unifi_device` and `unifi_setting`: manage Etherlighting via the new `etherlighting` blocks.** On switches with per-port LED lighting (e.g. USW Pro Max), `unifi_device.etherlighting` sets the per-switch `mode` (`speed` or `network`), `brightness` (1-100), `behavior` (`steady` or `breath`) and `led_mode` (`etherlighting` or `standard`); its fields are Optional+Computed with `UseStateForUnknown`, and `ether_lighting` is carried into the minimal update body, so a change is sent on update rather than only on adoption. `unifi_setting.etherlighting` sets the site-wide colors per link speed (`speed_overrides`) and per network (`network_overrides`), as 6-digit hex codes without the `#`. The setting block is opt-in like the others on `unifi_setting` and writes only the lists present in the configuration: a declared list replaces the controller's list (`[]` clears it), and an omitted one keeps the colors set in the UI (#666, from #463 by @angel-penchev)
- **`unifi_setting`: write-only RADIUS shared secret.** `radius_secret_wo` (Terraform 1.11+) sends the RADIUS shared secret at apply time without persisting it to state; increment `radius_secret_wo_version` to send a new value. It is mutually exclusive with `radius.secret`, which keeps its current behaviour, and requires the `radius` block. The pair sits at the root of the resource rather than inside `radius` because Terraform does not allow a write-only attribute inside a computed nested attribute, and `radius` is Optional+Computed (#648, from #628 by @l50)
- **`unifi_vpn_server` and `unifi_wireguard_peer`: IPv6 for WireGuard servers.** `unifi_vpn_server.subnet_ipv6` sets the server's IPv6 subnet (forces a new server, since the controller only accepts it at creation), `wireguard.ip_version` (`v4` or `v6`, default `v4`) chooses the WAN address family the server listens on, and `unifi_wireguard_peer.interface_ipv6` gives a peer its IPv6 tunnel address. Existing configurations plan no changes (#657, from #625 by @johnmerchant; #622)
- **`unifi_vpn_client`: `ipv6_subnet`.** Manages the WireGuard client's IPv6 tunnel address. In file mode it defaults to the IPv6 entry of the configuration's `Address` line, which used to be dropped. When unset, the controller's value is read into state and sent back on update, so an address set in the UI survives; removing the attribute keeps the current address rather than clearing it (#587 by @marcobox)
- **`unifi_site_to_site_vpn`: IPsec `tunnel_ip`, `tunnel_ip_enabled` and `remote_vpn_dynamic_subnets_enabled`.** `tunnel_ip` (CIDR) sets the tunnel IP and enables it unless `tunnel_ip_enabled` says otherwise, also when it is added to an existing tunnel; removing it from the configuration keeps the controller's value, so set `tunnel_ip_enabled = false` to turn it off. `remote_vpn_dynamic_subnets_enabled` can be enabled manually and is forced on (an explicit `false` is rejected) when `dynamic_routing` is enabled with empty `remote_subnets`; when unset and not forced on, it keeps the controller's value. Both it and `dynamic_routing` update the tunnel in place (#660, from #559 and #556 by @denisyfrolov; #560, #557, #558)
- **`unifi_wan`: `interface_mtu` and `interface_mtu_enabled`.** Model the WAN interface MTU, e.g. `1508` for PPPoE with RFC 4638 ("baby jumbo") so the session carries a full 1500. Both are Optional+Computed and taken from the controller when not set, so an MTU configured in the UniFi UI is kept. go-unifi v1.41.0 (go-unifi#117) sends both fields for WAN networks, which earlier go-unifi releases left out (#645, from #601 by @lewis-green; #673)

### 🐛 Bug Fixes

- **`unifi_setting`: importing a site's settings no longer plans an update that rewrites the live values.** `Read` refreshed only the sections already in state, so an import read nothing, and every section the configuration set (IGMP snooping, NTP, syslog, mgmt, ...) planned as an update that rewrote the controller's values. An import now reads every section the controller holds a document for, in full, and plans no changes for a configuration that matches the controller, whether it sets a section in full or only in part. A section the configuration does not set is carried in state and is never written back: `Update` now writes only the sections the configuration sets. To support this, `igmp_snooping`, `connectivity` and `global_switch` are now Optional+Computed; those three plus `radius` and `usg` keep their prior value when the configuration omits them; and the leaf defaults of `auto_speedtest`, `dpi`, `lcm`, `network_optimization` and `syslog` apply only to a section the configuration sets, as `syslog.netconsole.enabled` already did. Inside a section the configuration sets, a leaf it leaves out that has one of these defaults still plans to that default, so a partial configuration plans no changes only where those omitted leaves already hold their defaults on the controller. An import never reads the RADIUS shared secret or `mgmt.ssh.password` into state, so a configuration that sets `radius.secret` plans one sensitive update after import. `snmp`, `radio_ai` and `mdns` are not read on import. Likewise, the standalone `usg_geo` and `ips_suppression` documents are written only when the configuration sets `usg.geo_ip_filtering` or `ips.suppression`, not whenever their parent section changes (#668, from #620 by @l50)
- **`unifi_setting`: an `ips` update no longer duplicates the controller's honeypot entries.** The planned `ips.honeypot` list was appended to the live list instead of replacing it, so every existing entry was sent twice and the apply failed with an inconsistent result (#668, from #620 by @l50)
- **`unifi_setting`: a changed section sends only the keys that change.** v0.61.0 stopped writing unchanged sections, but a section that did change was still sent as the whole go-unifi struct, whose booleans have no `omitempty` (for example `mgmt` `alert_enabled` / `boot_sound` / `led_enabled`, `usg` `dhcpd_use_dnsmasq`, `ips` `restrict_torrents`, `rsyslogd` `debug`), so keys the controller never stored were written as `false`. Each write now compares the setting with the controller's stored document and sends only the keys that differ; the controller merges partial updates (#668, from #564 by @kubicgruenfeld)
- **`unifi_setting`: five attributes no longer turn off features the controller has enabled, including DPI and remote syslog.** Same defect as #543/#544 elsewhere, and `unifi_setting` is where it hurts most: one resource fronts many site-level settings as nested blocks, so declaring a block to manage a *single* attribute pulls in every static `Default` in that block - and the framework applies defaults (`TransformDefaults`) *before* it runs plan modifiers (`SchemaModifyPlan`), so each one overwrites what the controller holds. Measured against a live site, `dpi.enabled`, `syslog.enabled`, `syslog.log_all_contents`, `auto_speedtest.enabled` and `lcm.sync` all read `true` on the controller against a `false` default. The syslog pair is the sharpest: a configuration declaring the `syslog` block only to set the server address was writing `enabled = false` alongside it, **disabling the very logging it was configuring**; `dpi.enabled` likewise switched off deep packet inspection. Verified live by reproducing exactly that configuration - the plan wrote `enabled = false` and `log_all_contents = false` before the fix, and leaves both to the controller after. All five defaults are dropped; the attributes stay `Optional + Computed`, matching their neighbours (#544, #552)
- **`unifi_setting`: adding `global_switch` to an existing resource no longer fails with an inconsistent result.** When the state had no `global_switch`, the fields the configuration leaves out planned as null, and the read-back filled `acl_device_isolation`, `dhcp_snoop` and `dot1x_portctrl_enabled` from the controller, failing the apply although the settings were written. Unset fields now plan as unknown (#641, from #596 by @jautaxpo; #572)
- **`unifi_network`: an update sends only what the plan changes.** Update used to PUT a whole network built from the plan, so a changed attribute also resent every DHCP, IPv6 and flag field the provider encodes, and a DHCP block left out of the configuration had to be read back from the controller first so the PUT would not clear it. Update now encodes the prior state and the plan and sends only the keys that differ, together with the keys the controller validates with them: `vlan` and its flag, and the keys of `dhcp_guarding`, the DHCP range, `dhcp_server.boot`, `dns`, `ntp` and `wins`, `dhcp_relay`, `ipv6`, `ipv6.ra`, `ipv6.pd` and `dhcp_v6_server`. A `dhcp_guarding` or `dhcp_server` block left out of the configuration sends nothing. Adding a `dhcp_server` block sends every key the block sets, with the DHCP range derived from `subnet` when `start` and `stop` are unset, and leaves the controller's boot settings alone when `boot` is unset. A plan that changes nothing on the controller sends no request. Removing `vlan` fails before any request, because the controller rejects a null `vlan` and treats an untagged network as VLAN 1, which the Default network holds (#664, from #607 by @sergeychernyshov-code)
- **`unifi_wan`: an update sends only what the plan changes.** Update used to PUT a whole WAN built from prior state with only some planned values copied over, so changes to `username`, `password` and `networkgroup` never reached the controller, and every update resent `enabled`, `wan_vlan` 0 and empty `wan_dhcp_options` and `wan_ip_aliases`. Update now encodes the prior state and the plan and sends only the keys that differ, together with the other keys of the same nested object: `vlan`, `egress_qos`, `dns`, `dns.ipv6`, `dhcp`, `dhcpv6`, `dhcpv6.pd`, `smartq`, `upnp`, `load_balance` and `igmp_proxy`. Adding a `dns`, `upnp` or `load_balance` block sends only the values it sets, and `dns.ipv6` left out of the configuration keeps its prior value instead of planning a change. A plan that changes nothing on the controller sends no request. `password_wo` is still sent with every update while it is set (#664, from #608 by @sergeychernyshov-code)
- **`unifi_network`: importing the default LAN no longer plans `enabled` from `false` to `true`.** The controller stores the default LAN without `enabled`, and Read took the missing key as `false`. A missing key now reads as `true`, and an explicit `false` is kept. The `unifi_network` data source, `unifi_site_to_site_vpn`, `unifi_vpn_client` and `unifi_vpn_server` read `enabled` the same way (#664, from #607 and #608 by @sergeychernyshov-code)
- **`unifi_wan`: importing or updating a WAN no longer switches it off.** The controller omits `enabled` from WAN networks (Network 10.x has no enable toggle for a WAN), and the missing key was read as `false`, so an import planned `enabled = false` and every update sent it, turning the uplink off. A value the controller does send is used as is; when it omits the key, a known prior value (an explicit `enabled = false` included) is kept, and a WAN with no value yet reads as `true` (#649, from #617 by @l50; #600)
- **`unifi_wan`: `igmp_proxy.downstream_network_ids` for UniFi OS gateways.** These gateways keep the downstream side of the IGMP proxy as a list of network IDs next to `igmp_proxy_for`, which reads `some` while the list is non-empty, so a WAN with downstream networks ticked in the UI never converged. The new set manages that list; `downstream` follows it (`some` while it is non-empty, `none` when empty), accepts `some`, and is no longer carried over from state. A USG-era `lan` / `guest` without IDs is sent unchanged. The list reaches the controller with go-unifi v1.41.0 (go-unifi#117), which sends `igmp_proxy_downstream_networkconf_ids` for WAN networks (#642, from #594 by @jautaxpo; #592; #673)
- **`unifi_device`: `port_override` booleans send an explicit `false`.** go-unifi encoded the port override booleans with `omitempty`, so `autoneg = false` and every other `false` boolean was never sent, and any port change left (or put back) the controller's `true` on every port. They are pointers since go-unifi v1.40.0 (go-unifi#115), and a configured `false` now reaches the controller (#664, from #568 by @HalisCz; #567)
- **`unifi_device`: `port_override.tagged_networkconf_ids` is sent and read.** It was in the schema but always read as null and never written, so a configured value was dropped without warning, including the uplink tagging the `mgmt_network_id` description asks for. When set it is now sent and refreshed as a set, so the controller reordering or duplicating IDs causes no diff, and a configured `[]` clears the tagged networks. When unset, the controller's value is carried, so declaring a port for its name or profile no longer deletes its tagged networks (#669)
- **`unifi_device`: a declared `port_override` no longer strips the port fields the schema does not expose.** Fields such as `stp_edge_state`, `multicast_router_mode`, `link_debounce_auto` and `qos_profile` were never carried into a declared entry, so any controller-side value made it differ, the whole `port_overrides` array was sent, and the full-replace PUT deleted those fields from every port on the device. Every field go-unifi models but the schema does not expose is now carried from the controller's entry, and a test fails if a go-unifi bump adds one that is neither exposed nor carried (#652, from #561 by @kubicgruenfeld)
- **`unifi_device`: changing `bandsteering_mode` no longer fails with an inconsistent result.** The controller applies it to access points asynchronously, like the LED overrides, so the read right after the PUT still returned the old mode. The planned value now wins over that read, and the next refresh reconciles with the controller (#654, from #566 by @kubicgruenfeld)
- **`unifi_client`: an update no longer re-enables a fixed AP that was turned off.** With `fixed_ap_enabled = false` the controller keeps echoing the last `fixed_ap_mac`, and the provider read it back into state. The stale MAC then reached the plan, and any later update of the client sent it with `fixed_ap_enabled = true`, pinning the client to that access point again. A disabled fixed AP now reads as a null `fixed_ap_mac`, so updates leave it off; an enabled fixed AP still reports its MAC. Same defect as the `fixed_ip` and `local_dns_record` echoes fixed in #386 and #387 (#644, from #618 by @l50)
- **`unifi_client`: an update no longer re-enables a disabled network override.** With the override off, the controller keeps echoing the last override network, and the provider read it back as `network_id`, so the next update of the client switched the override back on. `network_id` now reads as null while the override is disabled, and an active override is switched off (its ID kept, as the UI does) when no `network_id` is planned. The `network_id` description now says it is UniFi's Network Override, not the network of `fixed_ip` (#653, from #565 by @kubicgruenfeld)
- **`unifi_port_forward`: a disabled rule is no longer re-enabled, and a `tcp` rule no longer widened to UDP.** The sharpest instance of the #544 class, because here the wrong default *opens* a hole instead of closing one. `enabled` defaulted to `true` and `protocol` to `tcp_udp`, and the framework applies defaults (`TransformDefaults`) *before* it runs plan modifiers (`SchemaModifyPlan`), so both overwrote the controller's value for an undeclared attribute. Measured on a live site with eight rules: 3 of 8 are disabled on the controller and 5 of 8 are `tcp`-only. Verified live on a rule that is **disabled and forwards to SSH** - importing it without declaring `enabled` planned `false -> true`, so an apply would have reopened the port to the internet, with `tcp -> tcp_udp` alongside it. Both defaults are dropped in favour of `UseStateForUnknown`. Note `enabled` is deprecated, but deprecation never protected anyone here: the attribute still works and its default still won. Its message is also reworded, because the old wording - "instead of disabling a port forwarding rule you can remove it from your configuration" - read as advice to delete the `enabled = false` line, a manoeuvre whose failure mode was a WAN port reopening. Keeping a rule declared and disabled is a legitimate pattern (maintenance access reopened periodically rather than rewritten each time), and the message now says so; it also notes that removing just the attribute is safe as of this change. Verified live in both directions: with the rule in state and the `enabled = false` line deleted, the plan keeps `enabled = false`; and a rule **created** with the attribute undeclared is written `enabled: false`, because the field has no `omitempty` and an unknown value serializes as `false` - so omitting the attribute never opens a port, on an existing rule or a new one (#544, #553)
- **`unifi_port_forward`: an omitted `wan.ip_address` no longer plans `"any" -> null` on every run.** The controller stores and returns `"any"` for a rule without a destination IP filter, but the attribute was `Optional` only, so a configuration that sets `wan` without `ip_address` could never match the state: every plan proposed clearing it, also right after an import. #162 made `"any"` a valid value; this makes it the computed value. `ip_address` is now `Optional + Computed` with `UseStateForUnknown`, so an unset value tracks the controller. Verified against a UXG Fiber on UniFi OS Server: the perpetual diff is gone and the `lifecycle { ignore_changes = [wan] }` workaround can be removed. A rule whose state still carries a `source_limiting` block written before v0.43.0 keeps planning that block away; `terraform state rm` plus `import` clears it (#640, from #582 by @simonzrln)
- **`unifi_port_profile`: `forward = "customize"` is accepted with `tagged_vlan_mgmt = "custom"`.** The plan-time refusal of `customize` on an untagged native network is skipped for `tagged_vlan_mgmt = "custom"`, where the controller keeps `customize`; the error message names it as a way out (#595 by @jautaxpo; #571)
- **`unifi_port_profile`: an unset `forward` follows `tagged_vlan_mgmt`.** Its `all` default made a profile with `tagged_vlan_mgmt = "custom"` that leaves `forward` out fail after apply, because the controller stores `forward` in step with `tagged_vlan_mgmt` (`all` for `auto`, `native` for `block_all`, `customize` for `custom`). The default is dropped and an unset `forward` is derived from `tagged_vlan_mgmt` (#639, from #597 by @jautaxpo; #593)
- **`unifi_radius_profile`: `interim_update.interval` no longer overwrites a profile the controller stores without one.** The static `1h0m0s` default planned `null -> 1h0m0s` on every adopted profile whose controller document has no interval (the built-in Default profile has none), and `ignore_changes` could not suppress it: Terraform core passes the prior null as configuration, and the default filled it in again. The `1h0m0s` default now applies when a profile is created; an existing profile keeps the controller's value, which may be none. The new `planmodifiers.StringDefaultOnCreateKeepNull` holds a null prior value on update instead of falling back to the default (#544; #643, from #619 by @l50)
- **Refreshing a state written without resource identities no longer fails with `Unexpected Identity Change` on Terraform 1.12 and newer.** Terraform 1.12+ asks the provider to upgrade the identity of every resource whose stored identity version is older than the current one, including resources that have no stored identity at all: state last written by Terraform < 1.12, or migrated from `paultyng/unifi`. Since v0.57.0 (#506) the shared version 0 upgrader filled the provider's site into that empty identity, which made it a stored identity with a null `id`. `Read` then either derived the full identity from state, which the framework rejects as a change (`unifi_firewall_group`, `unifi_firewall_rule` and others failed every plan), or passed the null `id` through (`unifi_network`, `unifi_wlan` and others). An identity upgraded from nothing now keeps every attribute null, which the framework treats as no identity yet, and `Read` and `Update` derive it from state; a stored v0.55.0 `{"id"}` identity is upgraded as before. An identity v0.60.0 already stored with a null `id` is repaired too: the identity version is now 2, and the upgrade from version 1 treats an identity without an `id` as absent, so `Read` derives it again (Terraform rejects any change to a stored identity, so it can only be fixed during the upgrade). Resources covered: `unifi_ap_group`, `unifi_client_qos_rate`, `unifi_dns_record`, `unifi_firewall_group`, `unifi_firewall_policy`, `unifi_firewall_rule`, `unifi_firewall_zone`, `unifi_network`, `unifi_port_forward`, `unifi_port_profile`, `unifi_power_supervisor`, `unifi_radius_profile`, `unifi_radius_user`, `unifi_site_to_site_vpn`, `unifi_static_route`, `unifi_traffic_route`, `unifi_vpn_client`, `unifi_vpn_server`, `unifi_wan`, `unifi_wireguard_peer` and `unifi_wlan` (#647, from #621 by @l50)
- **`unifi_vpn_server`: `wireguard.public_key` is populated.** It is documented as computed from the private key but was only copied from the API response, which never carries it, so it was always null. It is now derived from the private key (X25519, the same calculation as `wg pubkey`) when the controller does not return one. Existing state fills in on the next refresh without a planned change (#624 by @johnmerchant; #623)
- **`unifi_wlan`: the deprecated `bandsteering_mode` no longer plans `+ (known after apply)`, including a perpetual in-place update on unchanged WLANs.** The attribute is Optional+Computed and always reads back null, but carried no plan modifier, so whenever the framework saw the plan differ from the prior state it re-planned it as unknown. Besides real changes, that happens on an unchanged WLAN whose controller holds `mac_filter.policy = "allow"`: the nested `"deny"` Default trips the gate and `mac_filter` restores its own value, leaving `bandsteering_mode` as the only, never-converging diff. It now keeps its prior value with `UseStateForUnknown`. Plan-side only; the attribute is still neither read nor written (#591 by @user-cube)
- **`unifi_site_to_site_vpn`: IKE phase 1 settings are sent under the IKE keys.** `ike.encryption`, `ike.hash` and `ike.dh_group` were mapped to the generic `ipsec_encryption`, `ipsec_hash` and `ipsec_dh_group` fields.

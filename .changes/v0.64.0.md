## [v0.64.0] - 2026-10-31

Static defaults no longer overwrite the controller's values (#544). Every
resource that planned a schema constant over a value the controller already
held now takes that value from the controller when the attribute is not set,
so importing or adopting an existing object plans no change. Values a new
object needs are still applied, on create only, so new objects are created
exactly as before. go-unifi is now v1.43.0 (UniFi Network 10.6.109).

**Upgrade notes:**

- Attributes that used to plan a static default now show `(known after apply)`
  or keep the value already in state when they are not set. If a
  configuration relied on a default to *change* a live value (for example to
  turn a disabled rule back on), set that attribute explicitly.
- Numeric fields the controller stores as an empty value read as null instead
  of `0` since go-unifi v1.42.0. This affects data sources such as
  `data.unifi_network` (`vlan`, `wan.egress_qos`).
- Changelog entries are now changelog fragments (changie): contributors add a
  file under `.changes/unreleased/` with `go tool changie new` instead of
  editing `CHANGELOG.md`. See `CONTRIBUTING.md`.

### 🐛 Bug Fixes

- **`unifi_wlan` no longer resets an imported SSID's AP group, enabled/guest state or remaining toggles to the schema defaults.** The last static defaults on `unifi_wlan` are gone: 14 attributes (`is_guest`, `vlan_enabled`, `l2_isolation`, `proxy_arp`, `uapsd`, `fast_roaming_enabled`, `multicast_enhance`, `mlo_enabled`, `hotspot2conf_enabled`, `private_preshared_keys_enabled`, `nas_identifier_type`, `mac_filter.enabled`, `wpa3.fast_roaming`, `wpa3.enhanced_192`) now take the controller's value when unset, and `enabled`, `ap_group`, `mac_filter.policy`, `minrate_setting_preference`, `wpa.mode` and `dtim_mode` keep their defaults for a newly created WLAN only. Before, importing an SSID without declaring `ap_group` planned clearing its `ap_group_ids`, and a partial `mac_filter` block flipped an `allow` policy to `deny`. (#680, part of #544)
- **`unifi_network` and `unifi_wan` no longer plan static defaults over the controller's values.** An imported or adopted network no longer proposes re-enabling itself or its internet access, turning off IGMP snooping, isolation or DHCP guarding, or (when `dhcp_server` is declared without them) resetting the lease to 24h, re-enabling conflict checking and switching DHCP DNS/NTP/WINS off. An adopted WAN keeps its `type` (a PPPoE/static uplink was planned, and on adoption written, back to `dhcp`), its VLAN id, egress QoS, Smart Queue and enabled flag. Defaults that a new resource needs (`internet_access`, `dhcp_server.enabled`, `conflict_checking`, `leasetime`, `gateway_type`) now apply on create only. `egress_qos.enabled` is no longer sent as `false` when unset (#682, part of #544)
- **`unifi_firewall_policy` no longer resets controller values on adopted policies.** `protocol`, `description`, `logging`, `match_opposite_protocol`, `create_allow_respond` and the endpoints' `port_group_id`, `ip_group_id`, `port_matching_type` and `match_opposite_{ips,networks,ports}` drop their static defaults and keep the controller's value when not declared. `create_allow_respond` alone was wrong for 333 of 377 policies on a live site, and importing a grouped policy cleared its address and port groups. `enabled` still defaults to `true`, but only for a new policy. (#683, part of #544)
- **`unifi_nat` keeps a disabled rule disabled.** `enabled` defaults to `true` only on create. `exclude`, `logging`, `pppoe_use_base_interface` and the filters' `invert_address`/`invert_port` keep the controller's value instead of being reset to `false`. (#685, part of #544)
- **`unifi_port_forward` drops its last static defaults.** `logging` and `source_limiting.enabled` keep the controller's value, and `source_limiting.ip` no longer invents `"any"`: an unset source address is not sent. (#687, part of #544)
- **`unifi_firewall_rule` applies its defaults on create only.** An adopted rule keeps its `enabled`, `network_type` (`ADDRv4` is no longer rewritten to `NETv4`), `state` flags, `logging` and `protocol_match_excepted`. An omitted `source`/`destination` block no longer plans nulls over the controller's addresses and ports, which used to end in "inconsistent result after apply". New rules are created exactly as before. (#689, part of #544)
- **`unifi_radius_profile`, `unifi_radius_user`, `unifi_port_profile`, `unifi_power_supervisor`: static defaults no longer overwrite the controller's values on adopted objects.** Importing the built-in RADIUS `Default` profile planned `use_usg_auth_server = true -> false`, moving it off the gateway's RADIUS server. RADIUS users with a VLAN tunnel planned `tunnel.type` back to `3`. Server ports and tunnel types the controller stores as `""` (read as null since go-unifi v1.42.0) planned `null -> 1812` / `null -> 3` on every first apply. Attributes the controller always reports now come from it. Values that must be on the wire for a create (`autoneg`, `lldpmed.enabled`, the `dot1x`/`lldpmed`/`interim_update`/`vlan`/`tunnel` groups, the RADIUS server ports, the power supervisor settings) are applied to new objects only, and an existing object keeps the controller's value, null included. New objects are created exactly as before (#684, part of #544)
- **`unifi_client`: adopting a blocked client no longer unblocks it.** `blocked` carried `Default(false)` next to `UseStateForUnknown`, and the Default always wins, so an imported blocked client with `blocked` left out planned `true -> false`. Taking over an existing client with `allow_existing` also sent `blocked = false`. The Default is dropped, an unset `blocked` is no longer sent, and the controller's value is kept (#686, part of #544)
- **VPN resources no longer overwrite an adopted tunnel with schema defaults.** `unifi_vpn_server`, `unifi_vpn_client`, `unifi_site_to_site_vpn` and `unifi_wireguard_peer` planned undeclared attributes back to static defaults, because the framework applies defaults before plan modifiers: a disabled tunnel was re-enabled, a `wan2` tunnel moved to `wan`, an IKEv1 tunnel switched to IKEv2, a server put back on port 51820/1194 or narrowed from v6 to v4, `wan.ip = "any"` written over a server storing none, and a peer's `allowed_ips` cleared. Values the controller always supplies are now held from state; values a new tunnel has always been created with are applied on create only, so the create request is unchanged (#690, part of #544)
- **Routing resources no longer overwrite adopted routes and BGP with schema defaults.** An imported `unifi_static_route` or `unifi_traffic_route` disabled on the controller was re-enabled, a switch static route moved to the gateway, a traffic route's kill switch turned off (letting traffic leak past the VPN when it is down), and an enabled `unifi_bgp` configuration turned off and renamed. These are now held from state when undeclared; new routes are still created enabled on the default gateway and new BGP configurations keep `frr.conf` / `BGP Configuration` (#691, part of #544)
- **QoS and DNS resources no longer overwrite adopted objects with schema defaults.** A disabled `unifi_qos_rule`, `unifi_content_filter` or `unifi_dns_record` was re-enabled on import, a rule's burst allowance reset to `OFF`, a rate-limited `unifi_client_qos_rate` group lifted to unlimited, and a `unifi_dynamic_dns` entry on `wan2` planned for replacement. These are now held from state when undeclared; new objects are still created enabled, unlimited, with bursts `OFF` and on `wan` (#692, part of #544)
- **`unifi_firewall_policy` keeps an adopted IP/MAC binding and IPv6 interface ID match.** `match_mac`, `mac`, `iid` and `match_opposite_iid` drop their static defaults: a new policy is still created with `false`/empty, an existing one keeps the controller's values while the endpoint's `matching_target` is unchanged (switching the target resets them as before). `unifi_client_qos_rate` now accepts `qos_rate.max_up = -1` (unlimited), like `max_down`. New `unifi_vpn_server`, `unifi_vpn_client`, `unifi_site_to_site_vpn`, `unifi_static_route`, `unifi_qos_rule`, `unifi_content_filter` and `unifi_dns_record` resources now plan `enabled = true` instead of `(known after apply)`; the value sent is unchanged. (#693, part of #544)
